# Roadmap (на русском)

Это детальный, инженерный roadmap развития Chat Bot Constructor от текущего состояния к production SaaS-продукту.
Документ основан на серии аудитов кодовой базы и является источником истины для приоритизации — `README.md#roadmap`
содержит только сжатую, фазовую версию этого документа.

> Это переведённая версия [`docs/roadmap.md`](./roadmap.md). При расхождениях (например, после обновления
> оригинала) источником истины считается английская версия.

Продуктовая траектория, на которую опирается этот roadmap:

```text
Internal tool → Internal multi-user beta → Public beta → Self-service SaaS
```

## Как читать этот документ

- **P0** — обязательно, прежде чем приложением сможет безопасно пользоваться больше одного доверенного
  внутреннего аккаунта.
- **P1** — необходимо перед открытием продукта внешним, неконтролируемым пользователям (public beta).
- **P2** — необходимо для полноценного self-service SaaS (пользователи самостоятельно управляют своими ботами,
  аналитика, версионируемая публикация).
- **P3** — масштабирование и продвинутые возможности; ценно, но только после закрытия P0–P2.

Каждый пункт ниже обоснован текущей реализацией, а не является гипотезой. Ничто в этом документе не предлагает
переписывать работающий код — каждый пункт либо закрывает конкретный пробел, либо добавляет отсутствующую
возможность.

## Руководящие принципы

1. **Не мигрировать незащищённый код.** Выделение Telegram runtime в отдельный сервис (P2) идёт после того, как
   закрыты его пробелы в безопасности и надёжности (P0/P1) — перенос небезопасного, непротестированного runtime
   в новый сервис перемещает проблему, а не решает её.
2. **Сохранять существующие архитектурные решения, которые уже соответствуют production-требованиям.**
   Per-editor Zustand store, разделение `Flow`/`FlowSnapshot` на draft/published и framework-agnostic слой
   `entities/*/server` (service/repository) — корректные решения, их нужно расширять, а не заменять.
3. **Чинить реальную проблему, а не её проекцию.** Пробелы в ownership/authorization исправляются на уровне
   service/repository (слой, который позже станет собственной authorization-границей backend'а), а не
   точечными патчами в UI.
4. **Никаких технологий ради технологий.** Backend extraction, очереди сообщений, Redis, RLS и подобная
   инфраструктура вводятся только тогда, когда конкретная, наблюдаемая потребность продукта их требует — см.
   [Осознанно отложено / не планируется](#осознанно-отложено--не-планируется).

## P2 — Self-service SaaS

| # | Проблема | Почему это важно | Затронутый код | Сложность | Зависит от |
|---|---|---|---|---|---|
| P2.1 | Публикация не хранит историю — `FlowSnapshot` представляет собой одну upsert-строку на каждый `Flow` | Пользователи self-service будут ожидать возможность откатить неудачную публикацию; сейчас такой возможности нет, как и действия "unpublish" | `prisma/schema.prisma`, `entities/workflow/server`, `features/publish-bot` | M | Закрытые пункты P1 (это меняет тот же путь записи, который сначала должен быть безопасным) |
| P2.2 | Telegram runtime работает в том же процессе/деплое, что и frontend | Нагрузку runtime и frontend нельзя масштабировать или эксплуатировать независимо | `features/telegram-webhook/**` → новый сервис | L | P0.5, P0.7, P1.1, P1.3 (должен быть безопасным, протестированным и наблюдаемым перед выделением) |
| P2.3 | Нет документированного REST API — все мутации идут через Next.js Server Actions | Нет интеграционной поверхности для будущих клиентов (мобильные, сторонние, публичный API) | Новый слой поверх `entities/*/server/service.ts` | L | Может начаться параллельно с P2.2, переиспользуя тот же domain-слой |
| P2.4 | У собранных данных ответов ботов (`BotResponse`) нет UI или API для просмотра | Продукт пока не может выполнить обещание "просмотр аналитики использования бота" из заявленных продуктовых целей, несмотря на то что данные уже собираются | Новая фича поверх server-слоя `entities/bot`/`entities/workflow` | M | P1.7 (FK должен существовать до построения надёжных join/агрегаций) |
| P2.5 | Нет прикладного шифрования `Bot.token` сверх исправления в P1.6 | Централизация работы с секретами естественнее после появления выделенного backend-сервиса | `entities/bot/server`, будущий backend-сервис | M | P2.2 |
| P2.6 | Нет метрик, трассировки или health-check эндпоинта | После появления второго сервиса (P2.2) нет способа независимо мониторить его состояние | Новый backend-сервис | M | P2.2 |

## Граф зависимостей (между уровнями)

```text
P0.1 ─┬─► P0.2 ─► P0.3 ─► P0.4 (общий ownership helper)
      │
P0.5 (webhook secret) ──► P1.2 (rate limiting должен идти после, а не до, защиты webhook)
P0.7 (тесты runtime) ──┬─► P1.11 (E2E на publish/save/webhook)
                        └─► P2.2 (backend extraction — нельзя мигрировать непротестированный код)
P1.1 (идемпотентность) ────► P2.2
P1.3 (структурированное логирование) ─► P2.2, P2.6
P1.7 (FK у BotResponse) ─────► P2.4 (аналитика)
P1 (все пункты security/надёжности) ─► P2.1 (история публикаций затрагивает тот же путь записи)
P2.2 (backend extraction) ─┬─► P2.5 (централизованная работа с секретами)
                             └─► P2.6 (observability для отдельного сервиса)
P2.3 (REST API) ───────────► P3.4 (публичный API для третьих сторон)
```

Единственное жёсткое правило, закодированное выше: **P2.2 (backend extraction) не должен начинаться раньше,
чем будут закрыты P0.5, P0.7, P1.1 и P1.3.** Всё остальное можно переупорядочивать в зависимости от продуктовых
приоритетов внутри своего уровня.

## Roadmap по направлениям

### Frontend
- Исправить семантику `isDirty` (P1.5); добавить автосохранение.
- Удалить мёртвую фичу `workflow-actions` (P1.8).
- Сузить подписки Zustand/React Flow у нод Condition/Summary (P3.5).
- `error.tsx` / `global-error.tsx` (P0.9).
- UX-полировка редактора — undo/redo, copy/paste, горячие клавиши (P3.3) — сознательно в самом конце.

### Backend
- Ввести `assertBotOwnership` на уровне сервисного слоя (P0.4) — спроектировано так, чтобы позже стать
  собственной authorization-границей backend'а, а не патчем только для UI.
- Держать всю новую бизнес-логику внутри `entities/*/server/{service,repository}.ts`, свободной от
  Next.js-специфичных API (`headers()`, `revalidatePath`, cookies) — именно это делает P2.2/P2.3 инкрементальной
  миграцией.
- Выделить Telegram runtime в самостоятельный Node.js-сервис (P2.2), затем — документированный REST API для
  операций с ботами/workflow (P2.3).

### Database
- Индекс на `Bot.userId` (P0.6); FK от `BotResponse` к `Bot` (P1.7).
- Шифрование `Bot.token` at rest (P1.6), пересмотр централизации после появления backend-сервиса (P2.5).
- Моделирование истории публикаций вместо одной upsert-строки `FlowSnapshot` (P2.1).

### Telegram Runtime
- Валидация webhook secret-token, убрать токен из webhook URL (P0.5).
- Тесты для `engine.ts`, `controller.ts` и каждого обработчика ноды (P0.7).
- Идемпотентность через `update_id` (P1.1); `answerCallbackQuery` (P1.12).
- Выделение в отдельный сервис (P2.2), только после выполнения перечисленного выше.

### Security
- Закрыть все пробелы ownership/authorization (P0.1–P0.4) — единственный наивысший приоритет в этом roadmap.
- Безопасность webhook (P0.5).
- Rate limiting (P1.2), security-заголовки (P1.10), реальная валидация сессии в middleware (P1.4).
- Шифрование токена (P1.6 → P2.5).

### Testing
- Тесты engine/controller/handler для runtime (P0.7).
- E2E-покрытие для сценариев save/publish/webhook (P1.11).
- `tsc --noEmit` как явный шаг CI наряду с существующим пайплайном lint/test/build/e2e.

### Deployment / DevOps
- Исправить дефект install-шага в CI (P0.8).
- Добавить Dockerfile / манифест деплоя (P1.9).
- Добавить health checks и мониторинг для каждого сервиса после появления второго сервиса (P2.6).

### Analytics
- Не строить никакой UI до появления P1.7 (целостность FK).
- Начать с простого списка собранных ответов по каждому боту; агрегации/дашборды (расширение P2.4) строить
  только после проверки простого варианта на реальном использовании.

## Осознанно отложено / не планируется

Эти пункты намеренно исключены из P0–P2, потому что решают проблемы, которых у продукта пока нет. Возвращаться
к ним стоит только при появлении конкретной, наблюдаемой потребности:

- **Очереди сообщений / асинхронная обработка задач** для выполнения workflow — текущая синхронная модель
  выполнения в рамках одного запроса пока не демонстрирует проблем масштабирования (P3.1 фиксирует
  необходимость вернуться к этому при наличии реальных данных).
- **Row Level Security в Postgres** — весь доступ к данным идёт через Prisma с единой сервисной ролью; нет
  прямого доступа клиента к базе данных, который RLS могла бы защищать.
- **Микросервисы сверх схемы "frontend + один backend runtime-сервис"** — неоправданно при текущем масштабе
  продукта.
- **Kubernetes** — управляемой платформы (например, одного контейнерного хоста) достаточно для целевого
  масштаба; это была бы инфраструктура ради самой инфраструктуры, а не ради потребности продукта.
- **GraphQL** — не существует проблемы over-fetching/under-fetching, которая оправдывала бы его вместо REST.
