## Purpose

Аутентификация по email и паролю: регистрация, вход, выход, понятная обработка ошибок провайдера, детерминированная навигация после успешной аутентификации и защита маршрутов на основе проверенной сессии.

## Requirements

### Requirement: Registration signs the user in and lands them in the application

Успешная регистрация SHALL завершаться активной сессией и переходом на дашборд без дополнительных действий пользователя. Система MUST NOT оставлять пользователя на форме регистрации после успешного ответа провайдера.

#### Scenario: Successful registration lands on the dashboard

- **WHEN** пользователь отправляет форму регистрации с валидными данными и провайдер отвечает успехом
- **THEN** пользователь оказывается на дашборде `/{locale}` в состоянии «залогинен», а шапка приложения показывает его имя и кнопку выхода

#### Scenario: Locale is preserved after registration

- **WHEN** пользователь регистрируется, находясь на `/en/signup`
- **THEN** переход происходит на `/en`, а не на маршрут другой локали

### Requirement: Sign-in lands the user in the application

Успешный вход SHALL завершаться переходом на дашборд. Переход MUST быть следствием самого входа, а не побочным эффектом перерисовки страницы, и MUST происходить за один переход, без промежуточных редиректов.

#### Scenario: Successful sign-in lands on the dashboard

- **WHEN** пользователь отправляет форму входа с корректными учётными данными
- **THEN** пользователь оказывается на дашборде `/{locale}` в состоянии «залогинен»

#### Scenario: Locale is preserved after sign-in

- **WHEN** пользователь входит, находясь на `/en/login`
- **THEN** переход происходит на `/en`

### Requirement: Newly registered users can sign in without confirming their email

Подтверждение адреса электронной почты SHALL NOT быть обязательным условием входа. Пользователь, только что завершивший регистрацию, MUST иметь возможность войти повторно теми же учётными данными.

Это временное состояние: требование существует, пока у продукта нет собственного домена для отправки писем, и подлежит замене в change `transactional-email`, который вернёт обязательное подтверждение.

#### Scenario: Sign-in immediately after registration

- **WHEN** пользователь зарегистрировался, вышел из приложения и вошёл снова теми же email и паролем
- **THEN** вход проходит успешно, и система не требует подтверждения почты

### Requirement: Authentication failures are surfaced to the user

Любая неуспешная попытка регистрации или входа SHALL приводить к видимому пользователю сообщению на языке текущей локали. Система MUST NOT завершать неуспешную попытку без обратной связи в интерфейсе.

Известные состояния провайдера MUST иметь собственные формулировки; как минимум: неверные учётные данные, пользователь с таким email уже существует, превышен лимит попыток. Неизвестный код ошибки SHALL приводить к обобщённому сообщению об ошибке.

#### Scenario: Invalid credentials on sign-in

- **WHEN** пользователь вводит несуществующий email или неверный пароль
- **THEN** отображается локализованное сообщение о неверных учётных данных, и пользователь остаётся на странице входа

#### Scenario: Email already registered

- **WHEN** пользователь пытается зарегистрироваться с email, который уже занят
- **THEN** отображается локализованное сообщение о том, что аккаунт уже существует, и пользователь остаётся на странице регистрации

#### Scenario: Provider rate limit reached

- **WHEN** провайдер отвечает превышением лимита попыток
- **THEN** отображается локализованное сообщение с просьбой повторить позже

#### Scenario: Unknown provider error

- **WHEN** провайдер отвечает кодом ошибки, для которого нет отдельной формулировки
- **THEN** отображается обобщённое локализованное сообщение об ошибке, и подробности не показываются пользователю

### Requirement: Form submission state is always released

Элемент отправки формы SHALL возвращаться в активное состояние после завершения попытки аутентификации независимо от её исхода. Форма MUST NOT оставаться в состоянии загрузки после ошибки.

#### Scenario: Failed attempt releases the form

- **WHEN** попытка входа или регистрации завершилась ошибкой
- **THEN** индикатор загрузки исчезает, кнопка отправки снова доступна, и пользователь может повторить попытку

### Requirement: Route protection is based on a validated session

Решение о доступе к защищённым маршрутам SHALL приниматься на основании сессии, проверенной у провайдера аутентификации, а не по наличию cookie с определённым именем. Просроченная или недействительная сессия MUST трактоваться как отсутствие аутентификации. Если в ходе проверки сессия была обновлена, обновлённое состояние MUST сохраняться в ответе, чтобы последующие запросы видели её актуальной.

#### Scenario: Expired session cannot reach a protected route

- **WHEN** пользователь с просроченной и не подлежащей обновлению сессией открывает `/{locale}/editor/{id}`
- **THEN** он перенаправляется на страницу входа

#### Scenario: Refreshed session stays valid for subsequent requests

- **WHEN** сессия пользователя была обновлена при обработке запроса
- **THEN** следующий запрос того же браузера распознаётся как аутентифицированный без повторного входа

### Requirement: Unauthenticated users are redirected away from protected routes

Неаутентифицированный запрос к защищённому маршруту SHALL перенаправляться на страницу входа с сохранением текущей локали.

#### Scenario: Anonymous user opens the editor

- **WHEN** неаутентифицированный пользователь открывает `/ru/editor/{id}`
- **THEN** он перенаправляется на `/ru/login`

### Requirement: Authenticated users are redirected away from authentication pages

Аутентифицированный запрос к странице входа или регистрации SHALL перенаправляться на дашборд с сохранением текущей локали. Требование MUST выполняться для обеих страниц.

#### Scenario: Authenticated user opens the sign-in page

- **WHEN** аутентифицированный пользователь открывает `/ru/login`
- **THEN** он перенаправляется на `/ru`

#### Scenario: Authenticated user opens the sign-up page

- **WHEN** аутентифицированный пользователь открывает `/ru/signup`
- **THEN** он перенаправляется на `/ru`

### Requirement: Authentication entry points navigate on the first interaction

Элементы управления в шапке приложения, ведущие на вход и регистрацию, SHALL выполнять переход по первому клику и MUST быть доступны с клавиатуры. Разметка этих элементов MUST NOT содержать вложенных друг в друга интерактивных элементов.

#### Scenario: Sign-in control in the application header

- **WHEN** неаутентифицированный пользователь нажимает элемент «Войти» в шапке приложения
- **THEN** происходит переход на `/{locale}/login`

#### Scenario: Sign-up control in the application header

- **WHEN** неаутентифицированный пользователь нажимает элемент «Создать аккаунт» в шапке приложения
- **THEN** происходит переход на `/{locale}/signup`

### Requirement: Sign-out returns the user to the unauthenticated experience

Выход SHALL завершать сессию и приводить интерфейс в неаутентифицированное состояние без ручной перезагрузки страницы.

#### Scenario: User signs out

- **WHEN** аутентифицированный пользователь нажимает выход
- **THEN** сессия завершается, и пользователь видит неаутентифицированную версию `/{locale}` с элементами входа и регистрации
