## Context

- `runWorkflowEngine` (`features/telegram-webhook/lib/engine.ts`) выполняет `while (currentNodeId)` и останавливается только когда handler возвращает `shouldStop: true` (сейчас это `question` и `choice`) или `nextNodeId: null`. Линейные ноды берут `edgesBySource.get(id)?.[0]`.
- Обработчик `start` возвращает `nextNodeId: null`, поэтому ребро, ведущее в `start`, завершает диалог, а не зацикливает его. Это отдельный дефект графа, но не бесконечный цикл.
- Валидация — чистые функции в `entities/workflow/lib/validation` (`validateGraphStructure`, `validateNodeConnections`, `validateNodeData`), которые агрегирует `validateWorkflow`. Issue содержит `code`, `nodeId?`, `messageKey`. Переводов для `validation.*` ключей сейчас нет: UI показывает только количество ошибок.
- `validateWorkflow` вызывается только на клиенте: `usePublishBot` блокирует открытие диалога при `!isValid`, `useSaveWorkflow` сохраняет всегда и показывает warning. Серверной валидации при публикации нет (P1.14).
- Канвас (`widgets/workflow-canvas`) не задаёт `isValidConnection`. Доступ к актуальному состоянию стора без подписки — через `useWorkflowStoreApi().getState()` (уже используется в `useSaveWorkflow`).
- `WORKFLOW_NODES_CONFIG` (`model/nodes-config.ts`) — презентационная конфигурация нод (иконки, цвета, ключи переводов).

## Goals / Non-Goals

**Goals:**
- Один источник истины для «нода ожидания», общий для runtime, валидации и канваса.
- Одна реализация алгоритма поиска циклов, переиспользуемая валидацией и канвасом.
- Защита в движке, не зависящая от того, прошёл ли граф валидацию.

**Non-Goals:**
- Изменение поведения контроллера при ошибке движка (fallback-сообщение, сохранение сессии) — P1.16.
- Структурированное логирование — P1.3.
- Отображение текста ошибок и подсветка нод на канвасе, ограничение числа исходящих рёбер — P2.11.
- Перевалидация уже опубликованных снапшотов или миграция данных.

## Decisions

### 1. Правило: «нет циклов без ноды ожидания», а не «нет циклов вообще»

Внутри одного update ответы пользователя не меняются, поэтому повторный проход по ноде без ожидания (включая `condition`) детерминированно повторяется бесконечно. Цикл через `question`/`choice` прерывается ожиданием ввода — это легитимный паттерн «неверный ответ → спросить снова».

Альтернатива — запретить любые циклы. Отклонена: ломает реальные сценарии повтора вопроса и меню, к которому можно вернуться.

### 2. Семантика ожидания — в отдельном модуле `entities/workflow/model`, исчерпывающая по типам

Новый модуль (например, `model/node-semantics.ts`) с `Record<WorkflowNodeType, boolean>` (`waitsForInput`) и `isWaitingNodeType(type)`, реэкспорт через публичный API `entities/workflow`. `Record` заставляет явно решить вопрос для каждого нового типа ноды (P2.15) — компилятор не пропустит пропуск.

Альтернативы:
- Добавить флаг в `WORKFLOW_NODES_CONFIG`. Отклонена: это презентационная конфигурация, а runtime на сервере не должен зависеть от UI-модуля.
- Объявлять флаг на `NodeHandler` в runtime. Отклонена: валидация и канвас не могут импортировать из `features/telegram-webhook` (FSD), и знание разделилось бы на два места.

Инвариант (проверяется тестом): типы, для которых `waitsForInput === true`, — ровно те, чьи handler'ы возвращают `shouldStop: true`.

### 3. Алгоритм — один модуль в `entities/workflow/lib/graph`

- `findNodesInUnsafeCycles(nodes, edges): Set<string>` — строит подграф из нод без ожидания и рёбер между ними, находит сильно связные компоненты алгоритмом Tarjan (итеративно, без рекурсии, чтобы не упираться в стек на больших графах). Нода в цикле — если её SCC содержит больше одной ноды или у неё есть петля на себя. Tarjan выбран вместо DFS с тремя цветами, потому что спека требует отчёт по **каждой** ноде цикла, а DFS с цветами находит только факт обратного ребра.
- `wouldCreateUnsafeCycle(nodes, edges, { source, target }): boolean` — `false`, если source или target — нода ожидания; `true`, если `source === target`; иначе BFS из `target` по подграфу без нод ожидания до `source`. O(V+E), вызывается на каждый hover при протягивании связи — для сотен нод это микросекунды.
- Учитываются все исходящие рёбра (не только `[0]`): консервативно и корректно для `condition`; после P2.11 у линейных нод останется одно ребро, и результат совпадёт с поведением движка.
- Рёбра, ссылающиеся на несуществующие ноды, игнорируются.

### 4. Валидация — отдельная фаза `validate-cycles.ts`

Новый файл рядом с остальными фазами и вызов в `validateWorkflow`, а не расширение `validateGraphStructure`: фаза имеет свою ответственность и собственный тест-файл, а `validateGraphStructure` уже совмещает четыре проверки. Issue: `severity: 'error'`, `code: 'CYCLE_WITHOUT_WAITING_NODE'`, `nodeId`, `messageKey: 'validation.cycleWithoutWaitingNode'`. Переводы не добавляются — как и для остальных `validation.*` ключей (см. Risks).

### 5. Движок — проверка повторного посещения + жёсткий лимит, типизированная ошибка

- `Set<string>` выполненных за вызов нод без ожидания. Перед выполнением ноды: если она не ждёт ввода и уже в наборе — бросить ошибку `reason: 'cycle'`. Ноды ожидания в набор не попадают, поэтому возобновление `initialNodeId` и возврат к вопросу работают как раньше.
- Счётчик шагов с константой `MAX_STEPS_PER_UPDATE = 100`: при превышении — ошибка `reason: 'step_limit'`. Это страховка на случай будущих типов нод, неверно классифицированных в п. 2; при текущих правилах ацикличный проход ограничен числом нод, и лимит не должен срабатывать на реальных графах.
- `WorkflowExecutionLimitError extends Error` с полями `reason`, `nodeId`, `botId` — в `features/telegram-webhook/lib` рядом с движком.
- Ошибка, а не `return null`: возврат `null` выглядел бы как штатное завершение диалога, сбрасывал бы сессию и прятал проблему. Решение о реакции (fallback-сообщение, сброс сессии, логирование) принадлежит контроллеру и закрывается в P1.16/P1.3. До тех пор ошибку ловит существующий общий `catch` контроллера, сессия не сохраняется, и каждое новое сообщение даёт максимум один круг — ограниченное поведение вместо бесконечного.

Альтернатива — только лимит шагов. Отклонена: лимит в 100 всё равно отправил бы до 100 сообщений на update; проверка повторного посещения обрывает цикл после первого круга.

### 6. Канвас — `isValidConnection` через `getState()`

`useCallback` без зависимостей от `nodes`/`edges`, читающий их из `useWorkflowStoreApi().getState()` в момент вызова. Это не пересоздаёт колбэк на каждое изменение графа и не вызывает ререндер `ReactFlow`. Дополнительной проверки в `connectNodes` стора не добавляется: соединения создаются только через канвас, а валидация перед публикацией ловит остальное.

## Risks / Trade-offs

- [Уже опубликованный бот с циклом начнёт обрывать диалог вместо спама, без сообщения пользователю] → Это строго лучше текущего поведения; понятное сообщение конечному пользователю добавляет P1.16, ближайший пункт M1.
- [Сообщение об ошибке валидации не переводится — пользователь видит только счётчик ошибок] → Существующее ограничение для всех `validation.*` ключей; запрет на канвасе (`isValidConnection`) не даёт создать такой цикл через UI, а текст и подсветку добавит P2.11.
- [Классификация «нода ожидания» разойдётся с handler'ами при добавлении новых нод] → `Record<WorkflowNodeType, …>` + тест-инвариант из п. 2.
- [Валидация консервативнее движка: цикл по второму ребру линейной ноды, которое движок игнорирует, тоже станет ошибкой] → Такой граф и так вводит пользователя в заблуждение; P2.11 запретит несколько выходов у линейных нод.
- [Серверная публикация по-прежнему не валидирует граф] → Движок защищён независимо; проверка подключится автоматически, когда P1.14 начнёт вызывать `validateWorkflow` на сервере.

## Migration Plan

Миграций данных нет. Деплой одним релизом; откат — revert. Опубликованные снапшоты не меняются: движок применяет защиту к ним при следующем update.
