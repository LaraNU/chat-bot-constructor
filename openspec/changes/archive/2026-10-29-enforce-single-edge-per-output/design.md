## Context

Мотивация описана в proposal.md (раздел Why). Текущее состояние кода:

- Рантайм. `message`, `question` и `start` (через `getNextNodeId` в `engine.ts`) берут `edgesBySource.get(id)?.[0]`. `choice` ищет ребро по `sourceHandle === button.id`, `condition` по `sourceHandle === 'true' | 'false'`. Порядок в `edgesBySource` совпадает с порядком в массиве `edges`, то есть с порядком создания рёбер.
- Выходы на канвасе. У `start`, `message`, `question` и `summary` один source `Handle` без `id` (`sourceHandle` у ребра `null` или `undefined`). У `choice` по `Handle` на кнопку с `id = button.id`. У `condition` два `Handle` с `id` `'true'` и `'false'`. У `end` source `Handle` нет.
- `isValidConnection` в `widgets/workflow-canvas/ui/workflow-canvas.tsx` уже читает граф через `useWorkflowStoreApi().getState()` и вызывает `wouldCreateUnsafeCycle` из `entities/workflow/lib/graph`.
- Валидация — это чистые фазы в `validateWorkflow`. Проверки обязательных рёбер по типу ноды находятся в `validateNodeConnections`, проверки данных ноды — в registry `NODE_DATA_VALIDATORS` (сейчас `condition`, `choice`, `summary`). Переводов `validation.*` нет: UI показывает только количество ошибок.
- `WORKFLOW_NODE_SEMANTICS` (`entities/workflow/model/node-semantics.ts`) — исчерпывающий `Record<WorkflowNodeType, NodeSemantics>` поведенческих свойств, общий для рантайма, валидации и канваса. Сейчас в нём только `waitsForInput`.
- `attachmentIds` у `message` хранится, но рантайм его не читает и не отправляет.
- Capability `workflow-validation` вводит in-flight change `add-workflow-loop-guard`, в `openspec/specs/` её пока нет.

## Goals / Non-Goals

**Goals:**

- Одно правило кардинальности для канваса и валидации, реализованное в одном месте.
- Знание о том, какие выходы у типа ноды, хранится в `WORKFLOW_NODE_SEMANTICS`, а не в разрозненных `switch` по типам.
- Валидация ловит графы, которые уже сохранены с несколькими рёбрами из одного выхода.

**Non-Goals:**

- Изменение рантайма. После изменения у линейной ноды максимум одно ребро, и `[0]` становится корректным, а не случайным.
- Обнаружение рёбер с устаревшим `sourceHandle` (кнопка удалена, ребро осталось).
- Reconnect существующего ребра перетаскиванием конца: на канвасе он не включён.
- Подсветка проблемных нод и выходов на холсте.

## Decisions

### 1. Правило «одно ребро на выход», а не «одно ребро на линейную ноду»

Выход определяется парой `(source, sourceHandle ?? null)`. Одно правило покрывает и линейные ноды (единственный выход с `null`), и ветвящиеся (по выходу на кнопку или ветку).

Альтернатива: ограничивать только линейные ноды. Отклонена. Две стрелки с одной кнопки `choice` — та же ошибка (`choice-handler` использует `.find`, то есть тоже первое совпадение), а при правиле «на ноду» понадобились бы две проверки вместо одной.

Нормализация `sourceHandle ?? null` обязательна: React Flow сохраняет отсутствующий handle как `null`, а рёбра, созданные в тестах и фикстурах, как `undefined`.

### 2. Ветвление без условия не поддерживается

Рассмотренные трактовки нескольких выходов у `message`:

- «Выполнить все ветки». Отклонено: порядок отправки не определён, а сессия хранит одну текущую ноду. Если две ветки дойдут до `question`, непонятно, чей ответ ждать. Понадобился бы многокурсорный рантайм.
- «Случайная ветка» (A/B). Если она понадобится, это будет отдельный тип ноды со своими handle, а не неявное поведение `message`.

### 3. `NodeSemantics.outputs` — описание выходов в существующем модуле семантики

Добавляем поле `outputs: 'single' | 'perHandle' | 'none'`:

- `start`, `message`, `question`, `summary` получают `'single'`;
- `choice`, `condition` получают `'perHandle'`;
- `end` получает `'none'`.

Правилу кардинальности это поле не нужно, оно работает по ключу выхода. Поле нужно для предупреждения `NODE_HAS_NO_OUTGOING_EDGE`: оно применяется к `'single'`-нодам, кроме `start`, у которого уже есть ошибка `START_NODE_NOT_CONNECTED`. Кроме того, `Record` заставит явно решить вопрос о выходах для каждого нового типа ноды (P2.15).

Альтернатива: захардкодить список `['message', 'question', 'summary']` в валидаторе. Отклонена: знание о форме ноды разъедется по нескольким местам, и новый тип ноды молча выпадет из проверки.

### 4. Одна чистая функция в `entities/workflow/lib/graph`, общая для канваса и валидации

В `lib/graph` (рядом с `find-unsafe-cycles.ts`) появляются две функции:

- `getOutputKey(edge)` или эквивалентный хелпер группировки рёбер по выходу;
- `isOutputOccupied(edges, { source, sourceHandle }): boolean` для канваса.

Валидация группирует рёбра тем же хелпером и выдаёт по одному issue на выход с количеством рёбер больше одного. Так канвас и валидация не смогут разойтись в понимании «выхода», в отличие от текущего расхождения между BFS и рантаймом.

### 5. Канвас: проверка в `isValidConnection`, а не через `Handle isConnectableStart`

`isValidConnection` вычисляет `!isOutputOccupied(...) && !wouldCreateUnsafeCycle(...)`.

Альтернатива: в каждом компоненте ноды через `useNodeConnections` выставлять `isConnectableStart={false}` для занятого handle. UX лучше (нельзя даже начать drag), но правило размазывается по шести компонентам нод, каждая нода подписывается на рёбра, а у `choice` и `condition` нужна отдельная логика по handle. Отклонено в пользу одной точки, которая уже существует и читает стор без подписки. Улучшение UX можно сделать поверх, когда будет подсветка (P2.11).

React Flow при `connectionMode` по умолчанию (`strict`) нормализует соединение, начатое с target-handle, в `{ source, sourceHandle, target, targetHandle }`, поэтому проверка корректна при drag в обе стороны.

### 6. Размещение проверок валидации

- `MULTIPLE_EDGES_FROM_OUTPUT` и `NODE_HAS_NO_OUTGOING_EDGE` идут в `validateNodeConnections`. Это фаза «исходящие рёбра по типу ноды», и проверки соответствуют её назначению.
- `EMPTY_NODE_TEXT` — новые `messageNodeValidator` и `questionNodeValidator` в `NODE_DATA_VALIDATORS`, по одной строке в registry.
- Issue на выход содержит `nodeId` и `messageParams: { handleId, count }`, где `handleId` пустой для единственного выхода. Этого хватит будущей подсветке конкретного handle.

### 7. Пустой текст — ошибка, даже если есть вложения

Рантайм не отправляет `attachmentIds`, поэтому `message` с вложением и без текста упадёт в Telegram так же, как пустой. Когда рантайм научится слать вложения (`sendPhoto` с `caption` и т. п.), правило ослабляется до «пусто и нет вложений». Это изменение спеки, и делать его нужно вместе с поддержкой вложений.

## Risks / Trade-offs

- [Существующие черновики с ветвлением у `message` перестанут публиковаться] → Это намеренно: они и так работали не так, как нарисовано. Toast «validation failed» сообщает количество ошибок. Подсказку, где именно ошибка, даст подсветка из P2.11. В описании релиза нужно упомянуть новое правило.
- [Новая нода `message` с пустым текстом сразу даёт ошибку, и при автосохранении чаще появляется «saved with errors»] → Так уже ведут себя `condition` и `choice` без настроек. Сохранение не блокируется. Если шум станет проблемой, его решают на уровне UX уведомлений, а не ослаблением правила.
- [Пользователь не может «перевесить» ребро, протянув новое из занятого выхода] → Нужно сначала удалить старое ребро, у него есть кнопка удаления. Reconnect — отдельное улучшение.
- [Уже опубликованные снапшоты с несколькими рёбрами продолжают выполнять первое ребро] → Рантайм не меняется: поведение опубликованных ботов сохраняется. Без серверной валидации (P1.14) прямой вызов Server Action всё ещё может опубликовать такой граф, и рантайм детерминированно возьмёт первое ребро.

## Migration Plan

Миграции данных нет. Правило применяется при следующем сохранении или публикации. Откат — revert коммитов: данные и рантайм не затронуты.

Порядок архивации: если `add-workflow-loop-guard` заархивирован раньше, требования этого change добавляются к уже существующей `workflow-validation`. Если позже, этот change создаёт capability, а loop guard добавляет к ней свои требования. В обоих случаях дельты используют только `ADDED` и не конфликтуют.
