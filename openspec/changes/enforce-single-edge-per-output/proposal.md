## Why

Канвас позволяет протянуть из одного выхода ноды несколько рёбер (например, `message → M2` и `message → M3`), но движок у линейных нод следует только за первым ребром (`edgesBySource.get(id)?.[0]`). Граф показывает ветвление, которого в рантайме нет: какая ветка выполнится, зависит от порядка создания рёбер, а вторая ветка молча становится мёртвым кодом. При этом валидация считает такие ноды достижимыми (BFS идёт по всем рёбрам), то есть валидация и рантайм по-разному понимают граф. Это первая часть P2.11 из roadmap. Делать её сейчас стоит потому, что ошибку пользователь не видит ни в редакторе, ни при публикации.

Ветвление без основания для выбора (ответа пользователя или данных) не имеет корректной семантики. «Выполнить все ветки» противоречит модели сессии с одной текущей нодой, поэтому ветвление остаётся задачей нод `choice` и `condition`.

Попутно закрываются два соседних дефекта того же класса «редактор пропускает граф, который рантайм не выполнит»:

- `message` с пустым текстом проходит валидацию, а Telegram отклоняет `sendMessage` с пустым текстом. `question` с пустым текстом приводит к исключению в handler'е.
- Линейная нода без исходящего ребра (кроме `end`) молча обрывает диалог без финального сообщения.

## What Changes

- **Правило «одно ребро на один выход».** Из каждого выхода ноды допускается не больше одного исходящего ребра. Выход — это единственный выход линейной ноды (`start`, `message`, `question`, `summary`), каждая кнопка `choice` и каждая ветка `true`/`false` у `condition`.
- **Канвас** отклоняет соединение из выхода, у которого уже есть ребро. Проверка встраивается в существующий `isValidConnection` рядом с защитой от циклов.
- **Новая ошибка валидации `MULTIPLE_EDGES_FROM_OUTPUT`** нужна для графов, сохранённых до изменения. Она блокирует публикацию, сохранение черновика не блокирует.
- **Новая ошибка валидации `EMPTY_NODE_TEXT`** для `message` и `question` с пустым текстом или текстом только из пробелов.
- **Новое предупреждение `NODE_HAS_NO_OUTGOING_EDGE`** для `message`, `question` и `summary` без исходящего ребра.
- Семантика выходов каждого типа ноды задаётся в существующем `WORKFLOW_NODE_SEMANTICS`, а не дублируется по месту.

Рантайм не меняется. **BREAKING** (для пользователей редактора): черновики, в которых у одного выхода несколько рёбер или есть `message`/`question` с пустым текстом, нельзя опубликовать, пока граф не исправлен. Уже опубликованные снапшоты продолжают работать как раньше.

## Capabilities

### New Capabilities

- `workflow-validation`: правила валидации графа. Capability вводится in-flight change `add-workflow-loop-guard` и ещё не заархивирована в `openspec/specs/`. Этот change добавляет к ней требования о кардинальности выходов, пустом тексте и тупиковых нодах.

### Modified Capabilities

- `workflow-editor`: канвас запрещает второе ребро из одного выхода ноды.

## Impact

- `src/entities/workflow/model/node-semantics.ts`: описание выходов для каждого типа ноды.
- `src/entities/workflow/lib/graph/`: чистая функция проверки занятости выхода.
- `src/entities/workflow/lib/validation/`: `validate-node-connections.ts` (кардинальность выходов, тупиковые ноды), новые валидаторы `message` и `question` в registry `node-validators`.
- `src/widgets/workflow-canvas/ui/workflow-canvas.tsx`: расширение `isValidConnection`.
- Тесты валидации и анализа графа.
- Документация: `docs/roadmap.md`, `docs/roadmap-ru.md` (P2.11 частично), `docs/cursor-context.md`, если он описывает правила графа.
- Вне скоупа: подсветка ошибок на холсте и тёмная тема (остальная часть P2.11), серверная валидация публикации (P1.14), отправка вложений `attachmentIds` в рантайме, переподключение существующего ребра перетаскиванием (reconnect), ветвление по случайности (A/B-нода).
